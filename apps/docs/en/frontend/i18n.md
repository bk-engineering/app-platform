# i18n (next-intl)

<Status value="implemented" note="fully wired up, and the default locale now matches ADR-0011" />

Every page lives under a `[locale]` segment. There's no route without a locale prefix.

## File layout <Status value="implemented" inline />

```text
apps/web/src/core/i18n/
├── routing.ts       # defines supported locales + the default
├── navigation.ts     # Link/useRouter/redirect that automatically carry the locale
└── request.ts        # loads the message file for the current locale (server-side)
apps/web/
├── messages/
│   ├── th.json
│   └── en.json
└── src/proxy.ts       # middleware resolving locale from path/cookie/header
```

This layout is real and working in today's code — all four files exist and are wired correctly.

## `routing.ts` today

```ts
// apps/web/src/core/i18n/routing.ts
import { defineRouting } from "next-intl/routing";

export const routing = defineRouting({
  locales: ["en", "th"],
  defaultLocale: "th",
});
```

This matches [ADR-0011](/en/adr/0011-thai-default-locale) now — a user who hits the site with no locale prefix, or with an `Accept-Language` header next-intl doesn't recognize, gets the Thai page by default.

## Middleware (`proxy.ts`)

```ts
// apps/web/src/proxy.ts
import createMiddleware from "next-intl/middleware";
import { routing } from "@/core/i18n";

export default createMiddleware(routing);

export const config = {
  matcher: ["/((?!api|trpc|_next|_vercel|.*\\..*).*)"],
};
```

This middleware: reads path/cookie/`Accept-Language` to resolve the locale, redirects to a locale-prefixed path if there isn't one yet, and sets a cookie remembering the user's chosen locale for next time.

::: tip This `proxy.ts` will grow, not get replaced
Once [route protection](/en/frontend/auth-client#route-protection) is implemented, the same file will call `createIntlMiddleware` first and then check the session — see the full target-state code in the client session page, so we don't end up running two separate middlewares.
:::

## `request.ts` — loading messages

```ts
// apps/web/src/core/i18n/request.ts
import { getRequestConfig } from "next-intl/server";
import { routing } from "./routing";

type Locale = (typeof routing.locales)[number];

function isSupportedLocale(value: string | undefined): value is Locale {
  return !!value && (routing.locales as readonly string[]).includes(value);
}

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = isSupportedLocale(requested) ? requested : routing.defaultLocale;

  return {
    locale,
    messages: (await import(`../../messages/${locale}.json`)).default,
  };
});
```

`isSupportedLocale` guards against a stray locale value slipping past the middleware and crashing the `import()` — it falls back to `routing.defaultLocale` (`th`).

## Message files

```json
// apps/web/messages/th.json
{
  "HomePage": {
    "title": "app-platform",
    "subtitle": "Next.js + NestJS + zod contracts ที่แชร์กัน รันบน Docker พร้อม hot reload"
  }
}
```

```json
// apps/web/messages/en.json
{
  "HomePage": {
    "title": "app-platform",
    "subtitle": "Next.js + NestJS + shared zod contracts, running in Docker with hot reload."
  }
}
```

Both files' keys must match **exactly** — one namespace per page (`HomePage`, `DashboardPage`, ...), each namespace a flat object nested no more than two levels, so `useTranslations("HomePage")` stays readable.

::: tip Catch missing keys in CI, not at runtime
next-intl won't error at build time if a key is missing on one side — it just renders the raw key (`"HomePage.title"`) to the user. There should be a CI script diffing keys across every locale file instead of waiting for a user to report it.
:::

## Using it in a component

```tsx
// apps/web/src/app/[locale]/page.tsx
import { useTranslations } from "next-intl";
import { Button } from "@/core/ui/button";

export default function HomePage() {
  const t = useTranslations("HomePage");

  return (
    <main className="flex min-h-screen flex-col items-center justify-center gap-4 p-8 text-center">
      <h1 className="text-3xl font-semibold">{t("title")}</h1>
      <p className="max-w-md text-sm text-foreground/70">{t("subtitle")}</p>
      <Button>Get started</Button>
    </main>
  );
}
```

Links between pages use `Link` from `core/i18n/navigation.ts` only, never `next/link` directly — otherwise the locale prefix is dropped on navigation.

```tsx
// ✅ preserves the current locale automatically
import { Link } from "@/core/i18n";
<Link href="/dashboard">Dashboard</Link>

// ❌ navigates to /dashboard with no locale, forcing the middleware to redirect again
import Link from "next/link";
<Link href="/dashboard">Dashboard</Link>
```

## Adding a new locale or namespace

1. Add the locale code to `routing.ts` → `locales: ["en", "th", "..."]`
2. Create `messages/<locale>.json`, copying the structure of an existing file and translating every key.
3. Add a new namespace to every locale file at once, not one language at a time.
4. If the namespace is needed in a Server Component that doesn't sit under `NextIntlClientProvider`, use `getTranslations` (the async version) instead of `useTranslations`.

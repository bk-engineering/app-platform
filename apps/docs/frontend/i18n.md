# i18n (next-intl)

<Status value="implemented" note="ต่อสายครบและ defaultLocale ตรง ADR-0011 แล้ว" />

ทุกหน้าอยู่ใต้ `[locale]` segment เสมอ ไม่มี route ที่ไม่มี locale prefix

## โครงสร้างไฟล์ <Status value="implemented" inline />

```text
apps/web/src/core/i18n/
├── routing.ts       # นิยาม locale ที่รองรับ + default
├── navigation.ts     # Link/useRouter/redirect ที่ผูก locale อัตโนมัติ
└── request.ts        # โหลดไฟล์ข้อความตาม locale ปัจจุบัน (ใช้ฝั่ง server)
apps/web/
├── messages/
│   ├── th.json
│   └── en.json
└── src/proxy.ts       # middleware ตรวจ locale จาก path/cookie/header
```

โครงสร้างนี้ทำงานได้จริงในโค้ดวันนี้ ทั้งสี่ไฟล์มีอยู่และต่อกันถูกต้อง

## `routing.ts` ปัจจุบัน

```ts
// apps/web/src/core/i18n/routing.ts
import { defineRouting } from "next-intl/routing";

export const routing = defineRouting({
  locales: ["en", "th"],
  defaultLocale: "th",
});
```

ตรงกับ [ADR-0011](/adr/0011-thai-default-locale) แล้ว — ผู้ใช้ที่เข้าเว็บโดยไม่มี locale prefix หรือไม่มี `Accept-Language` ที่ next-intl รู้จัก จะได้หน้าภาษาไทยเป็นค่าเริ่มต้น

## Middleware (`proxy.ts`)

```ts
// apps/web/src/proxy.ts
import createMiddleware from "next-intl/middleware";
import { routing } from "@/core/i18n";

export default createMiddleware(routing);

export const config = {
  matcher: ["/((?!api|trpc|_next|_vercel|.*\\..*).*)"],
};
```

middleware ตัวนี้ทำหน้าที่: อ่าน path/cookie/`Accept-Language` เพื่อตัดสิน locale, redirect ไป path ที่มี locale prefix ถ้ายังไม่มี, และตั้ง cookie จำ locale ที่ผู้ใช้เลือกไว้สำหรับครั้งถัดไป

::: tip `proxy.ts` ตัวนี้จะขยายเพิ่มความสามารถ ไม่ใช่ถูกแทนที่
เมื่อ [ป้องกัน route](/frontend/auth-client#ป้องกัน-route) ถูก implement เต็ม middleware เดียวกันไฟล์นี้จะเรียก `createIntlMiddleware` ก่อนแล้วค่อยเช็ค session ต่อ — ดูโค้ดเวอร์ชันเป้าหมายเต็มในหน้า session ฝั่ง client เพื่อไม่ให้ต้องรัน middleware สองตัวซ้อนกัน
:::

## `request.ts` — โหลดไฟล์ข้อความ

```ts
// apps/web/src/core/i18n/request.ts
import { getRequestConfig } from "next-intl/server";
import { routing } from "./routing";

type Locale = (typeof routing.locales)[number];

function isSupportedLocale(value: string | undefined): value is Locale {
  return !!value && (routing.locales as readonly string[]).includes(value);
}

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = isSupportedLocale(requested) ? requested : routing.defaultLocale;

  return {
    locale,
    messages: (await import(`../../messages/${locale}.json`)).default,
  };
});
```

`isSupportedLocale` กัน locale แปลก ๆ ที่หลุดผ่าน middleware มาไม่ให้ crash ตอน `import()` — fallback ไป `routing.defaultLocale` เสมอ (ซึ่งตอนนี้คือ `en` ตามบั๊กด้านบน)

## ไฟล์ข้อความ

```json
// apps/web/messages/th.json
{
  "HomePage": {
    "title": "app-platform",
    "subtitle": "Next.js + NestJS + zod contracts ที่แชร์กัน รันบน Docker พร้อม hot reload"
  }
}
```

```json
// apps/web/messages/en.json
{
  "HomePage": {
    "title": "app-platform",
    "subtitle": "Next.js + NestJS + shared zod contracts, running in Docker with hot reload."
  }
}
```

key ทั้งสองไฟล์ต้อง**ตรงกันเป๊ะ** — namespace ต่อ page (`HomePage`, `DashboardPage`, ...) แต่ละ namespace เป็น object แบนไม่ซ้อนลึกเกินสองชั้น เพื่อให้ `useTranslations("HomePage")` อ่านง่าย

::: tip ตรวจ key ที่ขาดตอน CI ไม่ใช่ตอน runtime
next-intl ไม่ error ตอน build ถ้า key หายไปฝั่งหนึ่ง — มันแค่ render key ดิบ (`"HomePage.title"`) ให้ผู้ใช้เห็น ควรมี script เทียบ key ระหว่างไฟล์ทุกภาษาใน CI แทนที่จะรอผู้ใช้มา report
:::

## ใช้ในคอมโพเนนต์

```tsx
// apps/web/src/app/[locale]/page.tsx
import { useTranslations } from "next-intl";
import { Button } from "@/core/ui/button";

export default function HomePage() {
  const t = useTranslations("HomePage");

  return (
    <main className="flex min-h-screen flex-col items-center justify-center gap-4 p-8 text-center">
      <h1 className="text-3xl font-semibold">{t("title")}</h1>
      <p className="max-w-md text-sm text-foreground/70">{t("subtitle")}</p>
      <Button>Get started</Button>
    </main>
  );
}
```

ลิงก์ระหว่างหน้าใช้ `Link` จาก `core/i18n/navigation.ts` เท่านั้น ไม่ใช่ `next/link` ตรง ๆ — ไม่งั้น locale prefix จะหายตอนกด

```tsx
// ✅ คง locale ปัจจุบันไว้อัตโนมัติ
import { Link } from "@/core/i18n";
<Link href="/dashboard">แดชบอร์ด</Link>

// ❌ พาไปหน้า /dashboard แบบไม่มี locale ทำให้ middleware ต้อง redirect รอบใหม่
import Link from "next/link";
<Link href="/dashboard">แดชบอร์ด</Link>
```

## เพิ่ม locale หรือ namespace ใหม่

1. เพิ่มโค้ด locale ใน `routing.ts` → `locales: ["en", "th", "..."]`
2. สร้าง `messages/<locale>.json` โดย copy โครงจากไฟล์ที่มีอยู่แล้วแปลทุก key
3. เพิ่ม namespace ใหม่ในทุกไฟล์ locale พร้อมกัน ไม่แยกทำทีละภาษา
4. ถ้า namespace นั้นต้องใช้ใน Server Component ที่ไม่ผ่าน `NextIntlClientProvider` ให้เรียก `getTranslations` (เวอร์ชัน async) แทน `useTranslations`

::: warning สถานะโค้ดปัจจุบัน
| สเปกเป้าหมาย | โค้ดวันนี้ |
| --- | --- |
| `routing.ts`, `navigation.ts`, `request.ts`, `proxy.ts` | **มีครบและทำงานได้จริง** |
| `defaultLocale` เป็นไทยตาม ADR-0011 | ตั้งเป็น `"th"` แล้ว — ตรงสเปก |
| ไฟล์ข้อความ `th.json` / `en.json` | มีหลาย namespace ครบทุกหน้าที่ implement แล้ว (`Nav`, `DashboardPage`, `UsersPage`, `RolesPage`, `ThemePage`, `ProfilePage`, ฯลฯ) key ตรงกันทั้งสองไฟล์ |
| ตรวจ key ที่ขาดหายระหว่างภาษาใน CI | ไม่มี script ตรวจ |
| `proxy.ts` รวมการเช็ค session เข้ากับ locale middleware | ปัจจุบันมีแค่ next-intl middleware ล้วน ยังไม่เช็ค session (การป้องกัน route ทำที่ `(app)/layout.tsx` ฝั่ง client แทน) |
:::

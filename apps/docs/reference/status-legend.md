# ความหมายของสถานะ

<Status value="implemented" />

เอกสารชุดนี้เป็น **สเปกเป้าหมาย** ไม่ใช่รายงานสภาพโค้ด ป้ายสถานะบอกว่าหน้าไหนเชื่อได้แค่ไหน

## สามระดับ

| ป้าย | ค่าใน frontmatter | ความหมาย | สิ่งที่ควรทำ |
| --- | --- | --- | --- |
| <Status value="implemented" inline /> | `implemented` | โค้ดใน repo มีอยู่จริงและตรงกับหน้านี้ | ทำตามได้เลย |
| <Status value="in-progress" inline /> | `in-progress` | บางส่วนมีแล้ว บางส่วนยัง หน้านั้นระบุชัดว่าขาดอะไร | อ่านกล่อง "สถานะโค้ดปัจจุบัน" ก่อนใช้ |
| <Status value="planned" inline /> | `planned` | สเปกล้วน ยังไม่มีโค้ด | ใช้เป็นแบบตอน implement |

มีแค่สามระดับโดยตั้งใจ เพิ่มระดับที่สี่เมื่อไหร่ก็จะเริ่มเถียงกันว่าอันนี้ควรอยู่ระดับไหน

## ป้ายอยู่ที่ไหนบ้าง

### 1. Frontmatter — สำหรับให้เครื่องอ่าน

```yaml
---
title: Trace ID
status: planned
statusNote: ยังไม่มี genReqId, AsyncLocalStorage หรือการส่งต่อ header
---
```

`statusNote` ใส่เมื่อ `status` ไม่ใช่ `implemented` เขียนสั้น ๆ ว่า "ขาดอะไร" ไม่ใช่ "ทำอะไรได้บ้าง"

### 2. ป้ายระดับหน้า — บรรทัดแรกใต้ H1

```md
# Trace ID

<Status value="planned" />
```

ใส่ `note` ได้ถ้าอยากให้เห็นตั้งแต่บนสุด

```md
<Status value="in-progress" note="seed script ยังมีปัญหา" />
```

### 3. ป้ายระดับหัวข้อ — เมื่อบางส่วนต่างจากทั้งหน้า

```md
## ฝั่ง API ใช้ยังไง <Status value="implemented" inline />
```

ใช้เมื่อหน้าเป็น `in-progress` แต่มีหัวข้อหนึ่งที่ทำครบแล้ว (หรือกลับกัน)

::: tip อย่าใช้อีโมจิดิบในเนื้อความ
ใช้ `<Status />` เสมอ — มันแปลป้ายตามภาษาผู้อ่าน และเปลี่ยนหน้าตาได้จากที่เดียวถ้าวันหนึ่งอยากปรับ
:::

## กล่องเทียบสเปกกับโค้ด

หน้าที่ **ไม่ใช่** `implemented` ต้องมีกล่องนี้ ปกติอยู่ท้ายหน้า

```md
::: warning สถานะโค้ดปัจจุบัน
| สเปกเป้าหมาย | โค้ดวันนี้ |
| --- | --- |
| refresh token rotation + reuse detection | `auth.service.ts` แค่ verify แล้ว re-sign — token เดิมใช้ซ้ำได้ |
| ตาราง `RefreshToken` | ไม่มี — ระบบเป็น stateless ทั้งหมด |
:::
```

กฎของกล่องนี้

- อ้าง **ไฟล์จริง** เสมอ ไม่ใช่เขียนลอย ๆ ว่า "ยังไม่ได้ทำ"
- คอลัมน์ขวาต้องตรวจสอบได้ ถ้าผู้อ่านเปิดไฟล์แล้วเห็นไม่ตรง แปลว่าเอกสารเก่า
- หนึ่งแถวต่อความต่างหนึ่งเรื่อง อย่ารวบ

## ใครอัปเดต และเมื่อไหร่

| เหตุการณ์ | ต้องทำ |
| --- | --- |
| implement บางส่วนของหน้าที่เป็น `planned` | เปลี่ยนเป็น `in-progress` + เขียนกล่องเทียบให้ตรงว่าเหลืออะไร |
| implement ครบทั้งหน้า | เปลี่ยนเป็น `implemented` + **ลบกล่องเทียบทิ้ง** + ปลดแถวใน [Roadmap](/start/roadmap) |
| แก้โค้ดจน**ขัด**กับเอกสาร | แก้เอกสารใน PR เดียวกัน ไม่ใช่ไว้ทีหลัง |
| ตัดสินใจเปลี่ยนสเปก | เขียน ADR ใหม่ที่ supersede ของเดิม แล้วค่อยแก้หน้า |

::: danger เอกสารกับโค้ดต้องเปลี่ยนใน PR เดียวกัน
"เดี๋ยวค่อยอัปเดตเอกสาร" คือจุดที่ SSOT ตายเสมอ ถ้า PR แก้พฤติกรรมที่มีเขียนไว้ในเอกสาร ต้องแก้เอกสารมาด้วยกัน — และการอัปเดตสถานะเป็นแค่บรรทัดเดียว ไม่มีข้ออ้าง
:::

## ทั้งสองภาษาต้องตรงกัน

`status` ใน frontmatter ของหน้าไทยและหน้าอังกฤษต้อง**เท่ากันเสมอ** ถ้าไม่ตรง แปลว่าฝั่งใดฝั่งหนึ่งแปลค้างไว้ ดู [ADR-0015](/adr/0015-docs-as-bilingual-ssot)

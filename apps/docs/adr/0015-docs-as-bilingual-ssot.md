# 0015 · docs เป็น SSOT สองภาษา

<Status value="implemented" />

- **สถานะ:** accepted
- **วันที่:** 2026-08-07
- **หมวด:** process

## บริบท

`apps/docs` เดิมมีแค่ 4 หน้าและอธิบายเฉพาะสิ่งที่โค้ดทำอยู่แล้ว ขณะที่ boilerplate ที่ตั้งใจจะสร้างมีอีกมากที่ยังไม่ได้เขียน — auth, สิทธิ์, trace id, error envelope ถ้าปล่อยให้เอกสารตามโค้ด สเปกเหล่านั้นจะอยู่ในหัวคนเดียวและหายไปเมื่อเวลาผ่านไป

## การตัดสินใจ

**`apps/docs` เป็น single source of truth แบบ spec-first และมีสองภาษาเสมอ**

1. **เอกสารนำโค้ด** — หน้าเอกสารอธิบาย boilerplate ที่เป็นเป้าหมาย โค้ดตามเอกสาร ไม่ใช่กลับกัน
2. **ทุกหน้าติดสถานะ** — `implemented` / `in-progress` / `planned` ใน frontmatter และเป็นป้ายใต้ H1 ดู [ความหมายของสถานะ](/reference/status-legend)
3. **หน้าที่สเปกต่างจากโค้ด ต้องมีกล่องเทียบข้างกันที่อ้างไฟล์จริง**
4. **ไทยที่ root อังกฤษที่ `/en/` โครงสร้าง path เหมือนกันเป๊ะ**
5. **`ignoreDeadLinks: false`** — หน้าที่มีแค่ภาษาเดียวทำให้ `pnpm build` พัง
6. **โครงสร้าง sidebar/nav มาจาก `.vitepress/structure.ts` ชุดเดียว** ทั้งสองภาษาจึงไม่มีทาง drift เชิงโครงสร้าง

## ทางเลือกที่พิจารณา

### เอกสารตามโค้ด (เขียนหลัง implement)
ตรงกับความเป็นจริงเสมอ ไม่มีทางโกหก แต่สเปกที่ยังไม่ได้ทำจะไม่มีที่อยู่ — ซึ่งเป็นส่วนที่ทีมต้องการมากที่สุดตอนนี้

### สเปกอยู่ใน issue หรือเครื่องมือจัดการงาน
ผูกกับงานได้ดีและมีเจ้าของชัด แต่ issue ถูกปิดแล้วหายไปจากสายตา และค้นย้อนหลังยาก เอกสารอยู่ถาวรและอยู่ใน repo เดียวกับโค้ด

### สร้างเอกสารจากโค้ดอัตโนมัติ (OpenAPI, TypeDoc)
แม่นยำและไม่มีวันเก่า แต่ตอบได้แค่ "อะไร" ไม่เคยตอบ "ทำไม" และอธิบาย flow ที่ยังไม่มีโค้ดไม่ได้เลย ใช้เสริมได้ (Swagger ยังอยู่) แต่แทนกันไม่ได้

### ภาษาเดียว
ลดงานลงครึ่งหนึ่ง แต่ขัดกับ [ADR-0011](/adr/0011-thai-default-locale) ที่ตกลงว่าไทยเป็นภาษาหลักของทั้งผลิตภัณฑ์

### สองภาษาแบบไม่บังคับ (ปล่อยให้ /en/ ตามหลัง)
ยืดหยุ่นกว่า แต่ในทางปฏิบัติแปลว่าฝั่งอังกฤษจะค้างครึ่ง ๆ ตลอดไป การให้ build พังคือกลไกเดียวที่ได้ผลจริง

## ผลที่ตามมา

**ได้:** สเปกทั้งหมดอยู่ที่เดียวและอ่านได้ · เอกสารใช้เป็นใบสั่งงาน implement ได้โดยตรง · ป้ายสถานะทำให้รู้ทันทีว่าหน้าไหนเชื่อได้แค่ไหน · สองภาษาไม่มีทาง drift เพราะ build บังคับ

**เสีย:** ทุกหน้าต้องเขียนสองรอบ · เอกสารจะโกหกได้ถ้าไม่อัปเดตสถานะ — จึงต้องบังคับว่า **PR ที่แก้พฤติกรรมต้องแก้เอกสารมาด้วยกัน** · `ignoreDeadLinks: false` ทำให้ลืมมิเรอร์แล้ว build พังทันที (ตั้งใจ แต่เจ็บตอนแรก) · local search ต้องมีตัวตัดคำไทย

**ต้องทำต่อ:** เพิ่มขั้นตอน "build เอกสาร" ใน CI เมื่อทำ CI · พิจารณาสร้าง [Roadmap](/start/roadmap) จาก frontmatter อัตโนมัติด้วย `transformPageData` เมื่อหน้าเกิน 30

## เมื่อไหร่ควรทบทวน

ถ้าเวลาที่เสียไปกับการดูแลสองภาษาเริ่มทำให้ไม่มีใครอยากอัปเดตเอกสาร — เอกสารที่ไม่มีใครแตะเพราะกลัวงานเยอะ แย่กว่าเอกสารภาษาเดียวที่ยังมีชีวิต
